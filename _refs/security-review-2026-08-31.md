## 고친 것 — 코드

배포 후 프로덕션에서 전부 실측 확인함.

### 1. 로그인 페이지의 반영 문구 (가장 실질적)

`/auth/login`이 `?error=`에 담긴 값을 그대로 화면에 출력했다. React가 이스케이프하므로 XSS는 아니지만, **조작된 링크 하나로 진짜 도메인의 진짜 로그인 페이지, 진짜 비밀번호 입력창 바로 위에 공격자 문구가 뜬다.** 피싱 페이지를 우리가 호스팅해 주는 셈.

→ 알려진 코드 2개로만 해석하고, 나머지는 일반 문구로 대체 후 원문은 로그에만 기록.
→ 그 문구를 만들어 넘기던 콜백도 프로바이더 오류 텍스트 전달 중단.

### 2. `x-forwarded-host` 신뢰

콜백이 로그인 후 이동 주소를 이 헤더로 만들고 있었다. 클라이언트가 설정 가능한 헤더다. Vercel이 덮어쓰기 때문에 **실제로는 악용 불가능함을 프로덕션에서 확인**했지만, "플랫폼이 알아서 막아준다"에 의존할 이유가 없다.

→ 정식 도메인과 `*.vercel.app` 프리뷰만 허용, 그 외에는 요청 자체의 origin으로 폴백.

### 3. JSON-LD 삽입

`JSON.stringify` 결과를 `dangerouslySetInnerHTML`로 넣고 있었다. 브라우저는 그 블록을 `</script`를 만날 때까지 원문 텍스트로 읽으므로, 데이터에 `<`가 들어가면 태그가 조기 종료된다. 현재 단어·슬랭 데이터에는 없지만, 데이터가 늘어나도 계속 안전하려면 이스케이프가 필요하다.

→ `<` → `<`

### 4. `goal` 컬럼 권한 누락 (버그)

0013의 grant는 허용 목록이므로 나중에 추가된 컬럼은 명시하기 전까지 거부된다. 0036이 `goal`을 추가하면서 grant를 빠뜨렸다.

- 매직링크 가입: 정상 (`handle_new_user()`가 definer로 저장)
- **구글 로그인 가입: 온보딩에서 고른 목표가 조용히 버려짐** — 메타데이터에 goal이 없어 클라이언트 UPDATE가 유일한 경로인데 `permission denied for table profiles`로 실패

→ 마이그레이션 `0048_grant_profile_goal.sql` 작성. 클라이언트가 오류를 삼키던 코드도 제거.

### 판단 필요

**비밀번호 변경 시 본인 확인** (`security_update_password_require_reauthentication`)

효과는 가장 크다 — 지금은 세션만 살아 있으면 기존 비밀번호 없이 변경된다. 공용 PC에 로그인한 채 자리를 뜨면 계정을 통째로 잃는다.

**다만 지금 켜면 고장난다.** `/auth/update-password`는
`supabase.auth.updateUser({ password })`만 호출하며 인증 코드를 받는 절차가
없다. 설정만 켜면 서버는 코드를 요구하는데 화면은 묻지 않으므로 비밀번호 변경이
불가능해진다. 또한 `_require_current_password` 쪽은 비밀번호가 아예 없는
매직링크 사용자를 영구히 막는다.

제대로 하려면 코드 발송·입력 UI를 만들어야 하며 반나절 규모다. **사용자가
2026-08-31에 보류를 결정했다.** 같은 날 켠 비밀번호 변경 알림 메일이 위험의
상당 부분을 덮는다 — 막지는 못해도 주인이 즉시 알고 되찾을 수 있다. 결제를
붙이거나 사용자 규모가 커질 때 다시 볼 것.

## 운영 주의사항

Supabase Management API의 `/config/auth` 응답 본문에는 **`smtp_pass`와 `external_google_secret`이 평문으로 포함된다.** 이 점검 중 한 번 터미널에 그대로 출력됐다.

조회·수정 시 항상 끝에 다음을 붙일 것:

```
-o /dev/null -w "http=%{http_code}\n"
```

또한 PATCH는 원자적이다 — 필드 하나가 거부되면(예: HIBP) 요청 전체가 롤백된다.

# 부록 — 매직링크 조사 (같은 날 저녁)

`site_url` 변경을 실물 메일로 확인하는 과정에서 `otp_expired`가 반복돼 한때
**신규 가입이 막힌 것 아닌가** 의심했다. **결론: 앱은 정상이고, 테스트 방식이
잘못돼 있었다.**

## 무엇이 잘못됐나

`curl`로 GoTrue REST(`/auth/v1/otp`)를 직접 호출해 메일을 보냈다. 이 경로는
PKCE 없이 링크를 만들기 때문에, 인증 후 토큰이 주소의 **`#` 프래그먼트**에
실려 돌아온다. 프래그먼트는 브라우저 밖으로 나가지 않으므로 **서버는 볼 수
없다.**

우리 `/auth/callback`은 쿼리 파라미터(`code`, `token_hash`)만 처리한다. 그래서
프래그먼트 방식으로 돌아온 요청은 "아무 파라미터도 없음"으로 판정되어 마지막
줄의 `redirect('/auth/login?error=auth')`로 떨어졌다.

**앱의 실제 흐름은 영향 없다.** 브라우저의 supabase-js 클라이언트는 PKCE를
쓰므로 `?code=`가 쿼리로 돌아오고, 콜백이 정상 처리한다.

## 증거

- 18:04 발송 토큰이 18:18:48에 **소모됨**
- 같은 시각 세션 생성: `Mozilla/5.0 (Windows NT 10.0...)`, IP `183.103.178.126`
  — 사용자 본인 브라우저. **로그인은 성공했다**, 화면만 오류를 보여줬다

## 부수적으로 알게 된 것

- **새 매직링크를 발급하면 이전 링크는 즉시 무효가 된다.** 테스트 중 메일을 두
  번 보내는 바람에 첫 번째가 죽었고, 그것이 최초의 `otp_expired`였다. 테스트할
  때는 한 번만 보낼 것.
- `auth.sessions`에 `user_agent`가 `node`인 세션이 8/27, 8/28, 8/29, 8/31에
  남아 있다(AWS 계열 IP). 서버 측 로그인(콜백 라우트) 또는 다른 세션의 테스트
  스크립트로 보이며, 이번 건과는 무관한 것으로 판단된다. 확정하지 않았다.

## 남은 실제 개선 여지 (선택)

`/auth/callback`이 프래그먼트 방식으로 돌아오는 링크를 처리하지 못한다. 앱이
직접 만드는 링크는 전부 PKCE라 현재는 문제가 없지만, 외부 도구나 Supabase
대시보드에서 만든 링크로 들어오면 로그인이 된 채로 오류 화면을 보게 된다.
급하지 않다.

## 조사에 쓴 쿼리 (Management API)

```sql
-- 남은 일회용 토큰
select t.token_type, t.created_at
from auth.one_time_tokens t join auth.users u on u.id = t.user_id
where u.email = '<owner>';

-- 누가 링크를 사용했는가
select s.created_at, s.ip::text, s.user_agent
from auth.sessions s join auth.users u on u.id = s.user_id
where u.email = '<owner>' order by s.created_at desc limit 5;
```

`auth.sessions.user_agent`와 `ip`는 "사용자가 눌렀는가, 스캐너가 먼저 열었는가"를
가르는 가장 빠른 방법이다. 매직링크 문제를 다시 의심하게 되면 여기부터 볼 것.
